> 参考边界：老师示范项目是**课程管理系统**。本文只借鉴它的**流程和方法**（需求→原型→API→模型→代码→联调→验收、OpenAPI 契约、TDD、DTO/VO、UML 检查、黑盒测试、统一日志等），**不采用其课程/学期/教师学生等业务内容，不要求接入课程系统，也不照搬示例项目 ID、路径或业务规则**。

> 本项目范围以需求规格为准：市政公司统一权限管理系统，18 个应用、111 个组织、约 10,000 名员工、2,154 条清单权限；本轮按 RBAC0 主链整改，角色继承/约束/审计按课程阶段安排。
>
> 基线：`origin/main` 的 `4a2bed3`；本地整改分支 `feat/rbac0-menu-button-api`。本文写作时已完成成员 4 的 BE-03（请求标识/三层日志）和登录标识歧义修复，见第 6 节。

## 0. 结论

**设计文档和 ER 图已经按第一轮意见改对了，但代码、数据库、OpenAPI、前端原型仍然是旧模型。** 下次检查如果只看《概要设计说明书》，会认为问题只改了纸面；如果看代码和接口，第一轮指出的问题几乎原样存在。

当前最该做的不是再补文档，也不是继续扩充旧目录，而是：

> **把已经写对的设计落到数据库迁移、OpenAPI、后端代码和前端权限树四个产物里，并用可复现的测试和现场演示证明。**

最危险的是仓库里同时存在四套权限模型：

| 产物 | 权限模型 | 应用模型 | 部门管理员 | 权限—API |
| --- | --- | --- | --- | --- |
| 概要设计 / ER | `app_resource`（MENU/BUTTON）+ `sys_permission` | `app_application` | `admin_type` + `admin_dept_id` | `sys_api` + `sys_permission_api` |
| OpenAPI 0.3.0 | 功能点 × 动作，`sys:f339:read` 一类权限码 | 只有系统/模块/功能点 | 只有 `DEPT_ADMIN` 角色 | 没有 |
| 数据库 V001 / 导入脚本 | `app_system/app_module/app_function/sys_action` | `app_system` | 没有字段 | 没有 |
| 前端原型 / mock | `systems/modules/functions/actions` | `systems` | 只有角色 | 没有 |

**本轮不可妥协的目标：**

1. 权限 = 菜单或按钮，有 MENU/BUTTON 类型、父节点、应用归属；删除逻辑模型中的 `app_module/sys_action` 旧实体。
2. 登录带 `appCode`，只返回当前应用权限；18 个应用通过 `app_application` 管理。
3. 建立 `sys_api + sys_permission_api`，每个受保护 API 按 `operationId` 逐请求鉴权；未登记/未映射默认拒绝。
4. 用户表有 `admin_type/admin_dept_id`；部门管理员只能管 `admin_dept_id` 子树，不能分配管理类角色。
5. 持久化改用 Spring Data JPA，Service 写操作统一 `@Transactional`。
6. OpenAPI 0.4.0 按“界面原型 → 菜单/按钮目录 → API”重建，补全缺失接口。
7. DTO 按用例拆分，VO 按场景拆分，补中文 Javadoc，去掉散落的 `var`。
8. 保留已有正确行为：撤销权限下一次请求生效；现有保护规则、CAS/锁、回滚测试不能丢。

## 2. 本项目范围与第一轮问题

### 2.1 范围

- 18 个应用、111 个组织单元、约 10,000 名员工、2,154 条清单权限。
- 真实实现：系统管理后台 + 员工台账管理；其余 17 个业务系统以占位页演示权限效果。
- 本轮按 RBAC0：用户—角色—权限、菜单/按钮、应用归属、权限—API 映射、部门管理员、数据范围。
- 角色继承、SSD/DSD、激活角色、审计日志按课程后续阶段安排，不抢本轮主链。

### 2.2 第一轮检查仍然有效的问题

1. 权限没有真正表达成菜单/按钮树；数据库仍是“功能点 × 动作”。
2. 应用与权限的一对多关系没有落到数据库和 API。
3. 登录没有应用标识，返回全部权限，没有按应用隔离。

5. 部门管理员没有在用户表中可识别（`admin_type/admin_dept_id`）。
6. 持久化仍是 JDBC，不是 Spring Data JPA；事务覆盖不完整。
7. API 由需求文档整理，不是由界面原型逐动作驱动；OpenAPI 仍是 0.3.0。
8. DTO 集中在一个 `Requests.java`，响应多用 `Map`，缺 Command/Result 边界。

## 4. P0 整改项

### P0-1 统一权限模型，删除旧实体

**目标模型（与概要设计/ER 一致）：**

```text
app_application 1 ── * app_resource
                         ├─ resource_type = MENU   （parent_id 自关联，menu_level 1..3）
                         └─ resource_type = BUTTON （parent 必须是 MENU，action_code 固定 6 种）
app_resource 1 ── 0..1 sys_permission  （grantable=1 才有权限；模块导航节点 grantable=0）
sys_permission * ── * sys_api          （通过 sys_permission_api，带 mapping_type）
sys_user.admin_type / admin_dept_id    （部门管理员识别与管理范围）
```

**做法：**

1. 不改已执行的 V001，新增 `V002__menu_button_permission_and_api.sql`。
2. V002 建新表并从旧表回填：
   - `app_system` → `app_application`
   - `app_module` → MENU level 1，`grantable=0`
   - `app_function` → MENU level 2，`grantable=1`
   - `sys_action` → BUTTON，挂在对应功能点下
   - 旧 `sys_permission(function_id, action_id)` → 新 `sys_permission(resource_id)`，**权限码保持不变**
   - 每个功能点补一条菜单 `read` 权限
3. 旧表先保留为迁移期遗留，在数据字典/ER 标 `deprecated`，V003 再删除；逻辑模型和 ER 中不能再把 `app_module/sys_action` 当业务实体。
4. 同步改 `import_excel.py`、`verify_import.sql`、`schema.sql`、数据字典、ER 源文件和 PNG。
5. 菜单树装配：父菜单不可见 → 整个子树不返回；无菜单 `read` → 按钮列表为空；前端路由守卫再次检查。

**验收：**

- 18/115/359/2154 数量不变；随机 10 条旧权限码在新表中仍存在且授权可追溯。
- ER、数据字典、迁移、导入脚本只出现一套模型；没有 `app_module/sys_action` 作为授权核心。
- 任选用户管理页，能从应用 → 菜单 → 按钮 → 角色授权 → 所需 API 完整追溯。

### P0-2 登录带 `appCode`，只返回当前应用权限

**改动：**

- `Requests.Login` 增加 `@NotBlank String appCode`；门户用特殊值 `portal`。
- 会话保存 `userId`、`currentAppCode`、`credential`；登录后按 `appCode` 过滤权限。
- 登录返回：用户摘要、当前应用、该应用下的菜单/按钮树、`mustChangePassword`、授权版本。
- 新增 `POST /auth/switch-app`、`GET /portal/applications`、`GET /portal/menu?appCode=`。
- `GET /me/permissions?appCode=` 只返回当前应用；门户只返回可访问应用清单，不返回 18 个系统全部菜单。
- 前端登录页增加应用选择；切换应用时重新拉取权限树。

**验收：**

- 同一用户登录 `portal` 与登录 `hr`，返回的权限树不同；`hr` 响应里不出现其他应用权限。
- 直接请求 `/me/permissions?appCode=hr` 不泄露 `oa`、`sys` 等应用权限。
- 切换应用不需要重新输入密码，但重新校验账号状态和授权版本。

### P0-3 权限—API 映射，后端默认拒绝

**改动：**

1. 建 `sys_api`、`sys_permission_api`（字段按设计 6.2.2）。
2. 每个受保护 Controller 方法加稳定 `operationId`，与 OpenAPI、`sys_api` 三处一致。
3. 实现 `HandlerInterceptor`（或 `OncePerRequestFilter`）：
   - 认证：会话 → 当前用户；
   - 解析：`operationId` → `sys_api`；
   - 取权限：`sys_permission_api` → 所需权限码集合 + `permission_mode`（ANY/ALL）；
   - 比对：用户当前应用的有效权限；
   - 数据范围：交给 Service 做目标对象检查；
   - 未登记、未映射、映射为空 → 403 `API_NOT_REGISTERED`，绝不放行。
4. 启动时扫描 `RequestMappingHandlerMapping`，与 `sys_api` 对比；生产环境缺失即启动失败，测试环境契约测试失败。
5. 删除 `AuthorizationService.managementCodes` 硬编码；`rbac:*` 由映射数据和角色授权推导。
6. 占位系统按钮统一走 `POST /portal/placeholder-actions`，服务端校验请求中的 `permissionCode`。

**验收：**

- 合法 Cookie 直接 Postman 调无权限 API → 403，响应不含目标字段。
- 未登记 API → 403 `API_NOT_REGISTERED`，不是 200/404 放行。
- 所有受保护端点都能在 `sys_api` 找到；至少覆盖 ANY、ALL 两种映射模式。

### P0-4 部门管理员：字段、范围、任命接口

**改动：**

- `sys_user` 增加 `admin_type`（0 普通、1 超级、2 部门管理员）、`admin_dept_id`；CHECK：`admin_type=2` 时 `admin_dept_id` 非空，否则为空。
- `UserPO`、`MeService.userView`、用户列表/详情返回这两个字段。
- 新增 `POST /users/{id}/dept-admin`（任命/撤销），只有超级管理员可调用；同一事务更新字段 + 分配/撤销 `DEPT_ADMIN` 角色 + 递增版本 + 写审计。
- 管理范围改为 `admin_dept_id` 子树；不要用操作者自己的 `dept_id` 代替。
- 部门管理员不能分配 `ADMIN`、`DEPT_ADMIN` 或任何派生 `rbac:*` 的管理类角色；不能修改角色授权。
- 明确 `manager_user_id` 是业务负责人，不是授权管理员。

**验收：**

- ER、表、PO、接口返回都有 `admin_type/admin_dept_id`。
- 部门管理员只返回 `admin_dept_id` 子树；目标在范围外 403 `OUT_OF_SCOPE`。
- 分配管理类角色 403；任命/撤销字段与角色同时变化，失败两边回滚。

### P0-5 JPA + 事务

**改动：**

- `pom.xml`：`spring-boot-starter-jdbc` → `spring-boot-starter-data-jpa`；保留 MySQL/H2。
- `po/` 的 record 改 JPA `@Entity`，`mapper/` 改 `JpaRepository`；复杂查询用 `@Query` 或投影。
- Service 写方法统一 `@Transactional`；只读查询 `@Transactional(readOnly = true)`；整组替换、删除、任命、改密同一事务。
- 保留 `JdbcTemplate` 仅用于健康检查/初始化/迁移脚本。
- 版本冲突继续用 `role_version/permission_version`；如启用缓存，再加 `sys_authz_version`。

**验收：**

- 业务代码不再出现 `JdbcTemplate` 拼 SQL。
- `mvn clean verify` 通过。
- 授权集合、用户角色、任命部门管理员各至少一条“中途失败回滚”测试。
- 老师能看到 Entity、Repository、`@Transactional` 和回滚测试，而不是口头说明。

### P0-6 OpenAPI 0.4.0：按原型重建

**改动：**

- 以界面原型 + 菜单/按钮目录为输入，重建 `api/openapi.yaml`；需求文档只用来补每个接口说明。
- 补：`POST /auth/switch-app`、`GET /portal/applications`、`GET /portal/menu`、`POST /users/{id}/dept-admin`、`GET /catalog/applications`、`GET /catalog/menus`、`GET /catalog/permissions`、`GET/POST /catalog/apis`、`PUT /catalog/apis/{id}`、`PUT /catalog/permissions/{id}/apis`、`POST /catalog/validate`。
- 每个受保护操作：`operationId`、`x-required-permission`、数据范围、错误码。
- 角色继承/约束/审计标 `阶段二/三`，不混进阶段一“已实现”。
- 旧 `/catalog/functions`、`/permissions`、`/resources` 可保留为兼容，但标 `deprecated` 并说明替代关系。

**验收：**

- `python scripts/check_openapi.py` 通过。
- 契约操作集与运行 `/v3/api-docs` 完全一致。
- 每个页面/按钮都能在 `docs/api-map.md` 找到 API 和权限码；没有界面外资源。

### P0-7 DTO/VO 拆分与代码规范

- 一个用例一个 DTO：`LoginRequest`、`CreateUserRequest`、`UpdateUserRequest`、`ReplaceUserRolesRequest`……不要一个 `Requests.java` 装 11 个 record。
- 响应按场景拆 VO：`UserSummaryVO`、`UserDetailVO`、`MenuTreeVO`、`PermissionVO`……不要直接序列化实体。
- DTO/Controller 做 Bean Validation；Service 只做业务规则。
- 每个类、公开方法写中文 Javadoc；禁止 `var`；分页统一 `page/pageSize/total`。
- 数据库唯一键/CHECK 兜底；Flyway 只新增迁移，不改已执行迁移。
- 错误就地翻译成稳定业务码，不把表名判断堆到全局异常处理器。
- 先写会失败的测试，确认 RED，再写最小实现。

## 5. P1 整改项

### P1-1 前端从模拟演示升级为真实权限树

当前 `frontend/src/api/` 只有 mock/fixtures，没有 HTTP 客户端；路由守卫用旧权限码。建议：

- 新增 `frontend/src/api/client.js`，统一 `fetch`、错误码、401/403 处理。
- 登录带 `appCode`，会话保存 `currentApp`。
- 菜单/按钮树从 `GET /portal/menu` 获取，不在前端硬编码。
- 按钮按权限 `disabled`，路由按权限守卫，直接输入 URL 返回 403。
- 收到 403 强制刷新权限树；每个页面标注“本页用到的接口”。
- mock 与 http 可替换：生产构建走 http，演示构建才允许 mock 身份切换/延迟/失败注入。

### P1-2 登录标识与异常翻译（部分已完成）

- 登录标识跨字段歧义已修复：多候选拒绝登录；创建/编辑检查跨列撞值。导入脚本的跨列校验仍需与成员 1 对齐。
- `GlobalExceptionHandler` 现在仍按数据库错误消息含 `uk_*` 判断业务码。迁到 JPA 后应在具有业务语义的 Adapter/Service 处转换，Advice 只统一 HTTP 表示和兜底。

- 普通保存不手工 flush；确需事务内捕获约束时才用合适的 flush 方法。

### P1-3 批量写、迁移与大集合查询

- 避免数据库批量更新/删除；迁 JPA 后区分逐实体删除、批量 JDBC 写、JPQL bulk DML。
- 关联替换先读目标集合，按确定顺序处理，处于同一事务。
- 增加正式版本迁移机制或可审计升级流程，不依赖“重建空库”。
- 查询把范围、筛选、count、分页下推数据库；先保证范围在分页前计算。
- 不能用 SQL 工具耗时代替端到端性能；真实 MySQL/HTTP 测量。

### P1-4 UML 图与实现一致

- 现有图 4-1(a)/(b) 是目标设计类图，不是当前实现类图。重构后用真实类/方法生成实现级类图。
- 类图：Service 居中、名称/属性/操作三区、接口 `«interface»`、依赖虚线空心箭头、类框不重叠、线不穿框、依赖线不写文字。
- 顺序图：最左 `obj: 调用者`，普通对象 `objectName: ClassName`，静态方法 `«MetaClass»`；同步/回复/异常箭头区分，消息编号，执行条对齐，异常从实际抛出且仍激活的执行条返回。
- 每次生成 SVG + PNG，打开 PNG 目视检查；Mermaid 语法通过不等于布局合格。
- 设计图与实现图分开标注，不能把未实现方案标成现有实现。

### P1-5 测试、证据与标签

- 建立 `docs/testing/rbac-invariants.md`，每条带需求编号、期望行为/错误码、测试名。
- 黑盒覆盖正常、边界、异常；两套实现（如做）共用同一行为断言。
- 每份验收资料写提交、环境、命令、预期、实际、时间、执行者和未测项。
- 按实际完成节点创建标签（需求契约基线、模型闭环、JPA 闭环等），不补造历史。
- 不以覆盖率代替需求正确性；H2/mock/真实 MySQL/浏览器 E2E 分开写。

5. 撤销角色 → 下一次请求 403。
6. 停用用户 → 下一次请求 401。

## 9. 检查前演示与问答

### 9.1 现场演示（8 分钟）

1. 登录 `portal`，只看到可访问应用；切到 `hr`，只看到 `hr` 菜单/按钮。

5. 撤销按钮权/角色 → 用户下一次请求 403；退出后旧凭据失效。

### 9.2 可能的追问

| 问题 | 回答要点 |
| --- | --- |
| 为什么加部门？ | 1 万多名用户，超级管理员无法逐一管理；设部门管理员，管本部门及后代，缩小管理人数；不是为了展示组织架构。 |
| 部门管理员怎么识别？ | `admin_type=2` + `admin_dept_id`；同时持有 `DEPT_ADMIN`；两者同一事务维护；`manager_user_id` 只是业务负责人。 |
| 权限到底是什么？ | 一个菜单或一个按钮；菜单最多三级；按钮挂菜单下；父菜单无权限，子菜单和按钮都不可用。 |
| 18 个应用怎么管？ | `app_application 1:N app_resource`；登录带 `appCode`；只返回当前应用权限；门户只返回可访问应用清单。 |
| 前端隐藏按钮就够了吗？ | 不够；Cookie 拷到 Postman 也必须拒绝；后端按 method/路由→API→权限逐请求校验，未映射默认拒绝。 |
| 权限和 API 怎么对应？ | 按钮通常 1 个命令 API；菜单可对应多个查询 API；多对多；ANY/ALL 明确；按钮依赖父菜单读权限。 |
| 撤销权限怎么立即生效？ | 每次请求重新计算有效权限；如加缓存，缓存键含 `authz_version`；鉴权读主库。 |
| 为什么用 JPA？ | Java 课程要求；实体/Repository/事务边界清晰；不用 JDBC 拼 SQL；写操作统一 `@Transactional`。 |
| 怎么证明不是需求文档直接生成？ | 原型→菜单/按钮目录→OpenAPI（operationId）→代码；每阶段人工门禁；page→API 对照；契约测试。 |
| 旧的模块/动作实体呢？ | 逻辑模型删除；`app_module/sys_action` 只作为迁移期回填来源，V003 删除；新代码不再使用。 |
| 18 个系统还是 2 个系统？ | 本组按需求规格是 18 个应用；老师示范项目的课程管理业务不是本组范围。 |
