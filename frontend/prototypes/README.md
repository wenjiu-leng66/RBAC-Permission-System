# 成员 3：RBAC0 前端交互原型

本目录完成第一阶段可演示的权限页面与前端权限判断基础，不需要安装 Node.js，不调用真实后端。页面明确显示“交互原型 · 合成数据 · 未连接后端”。所有保存结果只在当前页面内存生效，刷新或“重置演示数据”恢复初始状态。

## 打开方法

1. 保留完整仓库目录结构。
2. 双击 `member3-rbac0.html`，使用 Edge、Chrome 或其他现代浏览器打开。
3. 如果只下载单个 HTML，样式、交互脚本和授权策略无法加载。应克隆完整仓库或下载仓库 ZIP 后解压。

文件关系：

```text
frontend/
├── prototypes/
│   ├── member3-rbac0.html   # 页面结构
│   ├── member3-rbac0.css    # 桌面与手机布局
│   ├── member3-rbac0.js     # 合成数据、表单状态和交互
│   └── README.md
└── src/authorization/
    └── rbac0-policy.js     # 共享 RBAC0 权限判断（经典脚本）
```

## 本阶段交付

| 页面 / 能力 | 可以直接操作的内容 |
|---|---|
| 角色授权 | 选择角色，搜索功能，勾选 / 撤销权限，保存、取消或清空勾选 |
| 资源目录 | 系统 → 模块 → 功能分层展示，按名称或权限码搜索 |
| 用户角色分配 | 为用户分配多个角色，完整替换 `roleIds`，显示权限并集预览 |
| 动态导航 | 根据当前身份权限显示管理页和业务页入口 |
| 按钮权限 | 文档查看、新建、编辑、审批分别使用独立权限码 |
| 页面访问检查 | 地址栏直接输入受限 hash 路径也检查授权；未登录显示登录占位，未授权或未知路径显示 403 |
| 演示状态 | 正常、空列表、权限加载中、保存失败和版本冲突 |

合成样例包含 **3 个系统、6 个模块、10 项操作权限、4 个角色、4 个用户**。角色与用户 ID 都有 `DEMO-` 前缀；这些授权并非原 Excel 的真实角色权限映射。没有把职位排序当作角色继承，也没有实现 RBAC1 或 RBAC2。

## 课堂演示顺序

### 1. 角色授权、取消与保存

1. 保持顶部“演示管理员”，进入“角色授权”。
2. 选择“演示文档编辑员”，勾选“审批文档”。右侧显示“有未保存修改”，已保存数量保持原值。
3. 点击“取消修改”，检查审批勾选恢复为未选。
4. 再次勾选并点击“保存授权”，稍候看到保存提示。
5. 顶部切换“演示文档编辑员”，进入“文档管理”，可以看到并操作审批按钮。
6. 切回管理员，撤销该角色的审批权限并保存。再次切换文档编辑员时，审批按钮消失。

### 2. 用户多个角色与撤销

1. 管理员进入“用户角色分配”，选择“演示普通员工”。
2. 同时勾选“演示文档编辑员”和“演示文档审批员”，保留原普通员工角色，查看去重后的权限预览。
3. 保存，切换普通员工，文档页面出现新建、编辑和审批操作。
4. 管理员撤销该用户的审批员角色并保存，切换普通员工：审批消失，新建和编辑保留。
5. 如果用户仍有其他提供相同权限的角色，撤销一个角色后该权限不会消失；这是 RBAC0 权限并集规则。

### 3. 菜单、直接访问与登录占位

1. 顶部选择“演示普通员工”，侧栏仅展示“文档管理”和“个人信息”。
2. 在地址栏末尾改为 `#/roles`，页面显示 403，不能通过地址绕过导航限制。
3. 输入 `#/unknown`，未知路径也显示 403。
4. 切换“未登录访客”，受保护页面显示登录占位。
5. 切换回管理员或点击“重置演示数据”恢复。

### 4. 查询与异常状态

1. 管理员进入“资源目录”，搜索“文档”“角色”或权限码；搜索不匹配词时展示无匹配资源。
2. 底部展开“演示与帮助”，选择“空列表”，查看角色、资源、用户或文档的空状态。
3. 选择“加载中”，导航不展示受保护入口，页面提示权限尚未加载。点击“完成加载”恢复。
4. 进入角色授权、修改勾选，选择“保存失败”后保存：提示错误，已保存权限不改变，草稿保留。
5. 选择“版本冲突”并保存：提示重新载入，已保存权限不改变。点击“重新载入”丢弃当前草稿。
6. 恢复“正常数据”，重新修改、保存；最后重置演示数据。

## 接入点与后续边界

- `member3-rbac0.js` 的 `session()` 是会话适配点。后续从登录接口获取身份，从用户有效权限接口加载 `permissions`；加载完成前保持 `permissionsLoaded: false`。
- 合成 `roles`、`users`、`permissions` 后续替换为接口返回值。保存角色权限应发送完整 `permissionCodes`，保存用户角色应发送完整 `roleIds`，以免只新增而不能撤销。
- 当前使用 500 ms 定时器模拟保存等待。真实保存需要等待后端成功后更新界面，失败不得先改已保存数据；遇到版本冲突应重新获取数据。
- 当前刷新权限通过重新计算内存里的角色权限并集；真实应用授权修改后，应重新获取当前用户权限或处理权限版本变化。
- hash 检查展示前端路由拦截方式；之后由实际前端框架路由守卫调用同一权限策略。
- RBAC1 需要明确的角色继承关系，RBAC2 需要经确认的约束规则；它们是后续阶段的独立工作。
- **前端隐藏菜单、按钮以及路由检查只能改善交互，不能替代服务端 API 授权。** 本原型没有真实登录、密码处理、令牌校验、数据库连接或云部署。

## 设计与使用说明

采用市政管理工作台的紧凑双栏布局：左侧选择角色或用户，右侧填写“授权作业单”；已保存 / 草稿状态和权限计数用于说明保存边界。工程蓝负责导航，绿色负责许可与完成状态，浅蓝灰背景减少长表单阅读负担。提供手机布局、键盘可见焦点和减少动画适配。

如果撤销了管理员本人的所有管理权限，页面会立刻失去管理入口。这是演示数据里的正常授权结果，使用底部“重置演示数据”即可恢复。真实系统是否应禁止撤销最后一个管理员，属于需要另外确认并在后端实现的业务约束。
